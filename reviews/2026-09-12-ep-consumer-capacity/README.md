# EP 消费者容量与调度验收

日期：2026-09-12 北京时间；真实请求发生在 2026-09-11 美股交易时段。

隔离数据：`/home/projects/quant/tmp/ep-consumer-capacity-20260912-live`，来自上一轮真实队列的 SQLite backup，原始发现时间、重试次数及证据均保留。

## 实现变化

| 文件 | 作用 |
| --- | --- |
| `src/breakouts/ep/consumers.py` | 三个独立消费者、非阻塞进程锁、交易日时间窗、运行日志和分阶段积压 |
| `src/breakouts/ep/price_news.py` | 有界双线程补查、首次处理名额、渐进退避及跨轮限流冷却 |
| `src/breakouts/ep/service.py` | HTTP 请求与时间预算的线程安全计数 |
| `src/breakouts/ep/pipeline.py` | 身份处理限额、原文首次/重试配额、原文执行时钟与数量 |
| `src/breakouts/ep/event_ingest.py` | 启用独立模式后，原采集任务不再抢做这三个消费者的工作 |
| `src/breakouts/ep/event_worker.py` | 独立模式、并发、单轮容量和期限配置；默认不启用独立模式 |
| `scripts/run_ep_consumer.py` | 计划、一次执行、只读状态入口，不调用模型或消息发送器 |
| `scripts/probe_ep_consumer_capacity.py` | 新建隔离副本，最多三轮真实新闻补查和一轮原文验收 |
| `deploy/systemd/quant-ep-*` | root、项目 `.venv`、独立 timer 与共享资源预算 |

原文选择额外修复了一处实际发现的公平性缺陷：先给重试预留名额，再从包含旧重试的“优先事件”集合补位，会把 8 个名额全部交给旧任务。现在优先事件集合只包含首次任务，重试单独分配。旧证据没有删除或改写。

## 调度和容量

以下是待启用模板，不是当前 SG 生产调度：

| 消费者 | 美东工作日触发时刻 | 单轮限制 |
| --- | --- | --- |
| price | 每分钟第 0 秒 | 既有价格请求预算、分页游标和数据契约 |
| news | 每分钟第 15 秒 | 32 只、2 路并发、最多 64 次新闻请求、40 秒请求预算 |
| source | 每分钟第 35 秒 | 最多 8 个事件、45 秒处理预算 |

timer 覆盖 04:00–15:59 ET；Python 按 XNYS 日历再次排除休市和提前收盘。使用 `America/New_York` 处理夏令时。上一轮仍在运行时不堆叠启动；进程锁也阻止 CLI 与 timer 重复消费。同一轮的待处理任务不是预先全部领取，耗尽预算后未领取任务仍可继续处理。

新闻同时存在足够首次任务和重试时，预留 24/8 名额；原文默认预留 6/2，并继续保留不同发行人及非财报新闻的覆盖。当某一组没有足够可选任务时才复用余量。名额是选择容量，不保证在网络超时情况下全部完成；实际领取数和完成数分别留档。

新闻没有新证据时按 5、10、20、30 分钟退避；出现新的证据修订后恢复 5 分钟。HTTP 429 冷却 5 分钟，401/403 冷却 1 小时，并停止该消费者的身份兜底请求。此冷却不是跨整个 Quant 项目的全局供应商限流器，其他策略仍有自己的请求预算。

每个消费者保留 `RUNNING` 检查点、完成报告、各阶段待处理/未首次处理/最老任务年龄。异常退出后进程锁自动释放，租约到期可重新领取；默认任务租约 600 秒，不承诺立即恢复。旧租约不能提交覆盖新结果。模型阶段继续原有节奏和预算，不因数据消费者加速而自动增加模型支出。

## 第一轮真实积压验收

留档：`sg-capacity.json`。三轮手动连续执行，不是经过 timer 运行三分钟的生产 SLA 验收。

| 指标 | 第 1 轮 | 第 2 轮 | 第 3 轮 |
| --- | ---: | ---: | ---: |
| 新闻消费者总耗时 | 34.949 秒 | 37.371 秒 | 36.206 秒 |
| 完成 stock + press 双接口检查 | 32 | 32 | 32 |
| 首次处理 | 28 | 32 | 32 |
| 新闻 HTTP 请求 | 64 | 64 | 64 |

- 共完成 96 次双接口检查，其中 92 只是首次处理；未首次处理的 NEWS 从 332 降至 240。
- 70 次检查在已抓取范围内没有新新闻，26 次观察到了新闻。每个接口只取前 25 条，不是全量新闻覆盖。
- 身份核对使用批量证券数据，三轮均未调用单股身份接口。新增 50 个待处理事件，SOURCE 从 3 增至 53。
- 随后一轮原文处理 8 个任务、18 次请求、23.15 秒，未新增匹配原文：2 个附件未匹配、1 个来源不完整、5 个窗口内无支持申报。不能把处理完成当作催化核准。
- 单进程 Linux `ru_maxrss` 峰值约 247.1 MiB。未采用 systemd 输出的异常偏小 Memory peak 作为资源结论。
- 旧发现时间完整保留，约 39 分钟的历史等待包含上轮验收和人工间隔，不伪装成本轮产生的延迟。

离线另以 332 个首次任务和 80 个已有重试验证连续 14 个模拟分钟周期，首次任务都得到处理。它证明有限队列在模拟快速接口下不被重试饿死，不是实际网络、持续新增候选下的完成时间承诺。

## 并行资源检查

留档：`sg-overlap.json`。三个独立 Python 消费者同时运行，共用隔离队列，没有修改生产数据：

- 价格限定 500 只、5 次请求，15.24 秒完成；这是部分扫描，不是全市场扫描完成。
- 新闻完成 32 次双接口检查，其中首次 24、重试 8，38.739 秒完成。
- 原文 8 个任务命中已有结果缓存，2.687 秒完成。这一轮也暴露了随后修复的原文重试挤占问题。
- 三进程采样合计峰值 RSS 592.3 MiB、PSS 393.9 MiB，采样间隔 0.2 秒；不包括既有模型和 Web 进程，也不是最坏负载上界。

SG 实际约 1963 MiB 内存，检查时可用约 999 MiB。模板限制三个数据消费者共享 CPU 75%（不是双核各 75%）、MemoryHigh 512M、MemoryMax 640M；单服务 MemoryMax 384M、超时 120 秒。既有模型/网页服务不在这个新 slice 内，正式启用仍需观察整机余量。

## 上线步骤

1. 冻结验收版本并备份生产配置、SQLite 和当前 release 指向；不要覆盖并行开发中的本地变更。
2. 在 SG 停止旧 timer 并等待在途旧 worker 结束，部署包含本轮入口的新 release，避免旧进程与新消费者同时使用旧编排逻辑。
3. 将生产配置显式设置 `independent_consumers_enabled=true`，价格扫描配置及独立数据库验收后再设置 `price_discovery_enabled=true`。保留 Discord 频道、密钥路径、模型预算及已有 outbox，不复制验收配置到生产。
4. 安装本轮 `quant-ep-consumer@.service`、共享 slice 和三个 timer；先逐个执行计划检查、受限运行和状态检查，再启用 timer。旧模型/消息 worker 恢复原有调度，不提高调用预算。
5. 检查每轮首次处理数、SOURCE 匹配率、ANALYSIS 积压、429 冷却、价格游标推进，以及总内存和重启次数。必要时先降低单轮任务数或暂停新 timer，不能通过放宽证据审核掩盖积压。

当前生产未启用这些 timer。因此本轮吞吐数据只能说明隔离验收能力，不能声称用户频道已经按新频率运行，更不能声称已完整复刻对方 EP。

## 最终回归与修复复验

SG 最终扩展回归：`pytest tests/ -q -k ep`，**759 passed、691 deselected**，153.37 秒，0 错误、0 失败。包含消费者并发、限流、配额、租约恢复、队列与既有 EP 路径；仅有既有 Starlette 依赖弃用警告。留档 `ep-final-tests.xml`。早期扩展回归为 757 项通过，之后增加了两项容量/原文公平性回归。

本地针对性回归先通过 63 项；增加跨轮容量测试后有一次本地 pytest 进程无输出停滞，核对 PID 后已终止。该进程停滞原因未在本轮定位，不能称本地最终全套通过；最终验收使用 SG Linux 的完整上述测试。

systemd 模板通过 SG `systemd-analyze verify`，仅输出服务器已有 `tat_agent` 的旧 PID 路径警告。日历解析确认美东分钟间隔，未安装或启用 timer。

原文配额修复后的第二次并行验收留档 `sg-overlap-final.json`，使用同一隔离副本原有时间戳，没有重置重试或回填成功：

| 消费者 | 实际处理 | HTTP 请求 | 消费者耗时 |
| --- | --- | ---: | ---: |
| price | 从游标 500 推进至 1000，检查 500 只，27 个暂定价格观察 | 5 | 18.12 秒 |
| news | 32 次双接口检查，首次 24、重试 8 | 64 | 41.797 秒 |
| source | 8 个事件，首次 7、重试 1 | 11 | 10.4 秒 |

原文在当时的发行人去重等选取约束下只有一个重试入选，剩余名额归还首次任务。SOURCE 缺口仍明确保留：3 个来源不完整、4 个窗口内无支持申报、1 个附件未匹配，未产生新的 ANALYSIS 任务。三进程均正常退出，整个并行验收 46.307 秒；采样合计 PSS 峰值约 400.4 MiB、RSS 峰值约 610.5 MiB，不含既有模型与 Web，也不代表整日或大 PDF 最坏负载。

这验证了三消费者可以在受限 SG 环境中并行推进，以及首次任务不会被旧重试占满；**没有验证全市场每分钟扫描完成，也没有证明完整原文覆盖或模型分析时效**。接下来是按上述步骤切换 SG 生产并观察真实调度，而非继续调推送文案。
