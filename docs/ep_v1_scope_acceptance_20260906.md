# EP 第一版范围与验收标准

日期：2026-09-06。状态：**数据能力验证已完成，以下开发和部署范围待确认；没有执行生产接入。**

依据：[数据能力报告](ep_data_capability_audit_20260906.md)、[17 个案例对照](ep_case_acceptance_matrix_20260906.md)。

## 1. 建议决策

**先做有证据的事件观察雷达，不把未验证的盘前量伪装成可交易 EP。**

分成两个可独立验收的阶段：

| 阶段 | 交付能力 | 明确不承诺 |
|---|---|---|
| v1A：事件观察 shadow | 新闻/财报发现、证据与版本留存、财报初筛、催化分析、候选状态和本地报告 | 与截图一致的盘前量比、正式价格触发、生产 Discord 推送 |
| v1B：完整行情与提醒 | 验证盘前数据后加入同钟量、流动性和开盘后升级；经授权接入独立通知 | 盈利保证、与对方完全相同的名单或主观评级 |

`EP_GAP_THROUGH_CUP` 的交易触发单独验收，不能因 v1A 新闻分析完成就默认上线。两个阶段都保留现有杯柄、多因子和板块轮动逻辑，不能通过放宽杯柄阈值来冒充 EP。

## 2. 时间线与数据流

```text
全市场证券身份 + 新公告/财报日历        合格的行情异动数据
                   \                  /
                    独立 EP 事件候选集合
                              |
                 原文获取、去重、事件归属与时效
                              |
              结构化事实 + 来源片段 + as-of 版本
                              |
              规则校验 + 可选 LLM 证据抽取/解释
                              |
           催化质量 / 行情质量 / 风险 / 缺失项分别输出
                              |
                 EP_WATCH 观察状态及变化记录
                              |
          [后续独立验收] T-1 杯 + gap-through + 开盘确认
                              |
                独立 outbox -> 专用 Discord 频道
```

新闻流不经过现有 Return20/ADR 硬筛，也不以“已经在 600 只日线候选里”为发现前提。EP 和杯柄可以观察同一股票，但各自保存原因、版本和状态。分钟数据可以共享有质量契约的缓存，不能共享或覆盖对方策略状态。

## 4. 催化判断怎么落地

### 4.1 先识别事实，再判断质量

事件类型至少区分：财报、指引变化、商业合同、并购买方、被收购方、交易终止、监管/临床、融资/回购、其他直接事件、行业/政策联动、未知。

“直接”需要发行人、子公司或可验证的交易对手角色证据。EOSE 自己参与项目就是直接事件，即使经济影响尚不清楚；同板块涨了不能自动证明某只股票只有主题催化。没有抓到公告只能标记 `NO_EVIDENCE_FOUND_IN_FETCHED_SCOPE`。

时效以交易 session 计算，记录 `published_at`、`first_seen_at`、事件首次公开时间和修订时间。前夜财报保留到次日开盘；前一日盘中消息可作为延续观察，初版可配置保留两个 session。转载旧文不能刷新首次事件时间。这个保留窗口是工程初值，必须通过样本验证，不是截图可反推出的精确参数。

### 4.2 财务计算由确定性代码完成

- 实际/预期须具有相同公司、期间、币种、单位和 EPS 口径；无法确认时展示两项原值并标 `BASIS_UNVERIFIED`，不自动声称 beat。
- 口径已确认且预期不接近零时，可算 `(actual - estimate) / abs(estimate)`；亏损 EPS 不用负分母，接近零改报绝对差。
- “上调指引”比较同期间的新旧指引；“高于市场”比较事前 consensus，两者独立。
- ARR、NRR、cRPO、同店、book-to-bill 等保留单位、期间、来源和前值，不能跨指标或季度直接说加速。
- 税项、退款、资产收益、回购影响单列风险。没有可核准的调整明细，不自行把 GAAP EPS 改成“真实 EPS”。

### 4.3 LLM 的角色和 API 需求

数据采集、去重、数学计算和规则测试不需要 AI API。要接近截图那种行业指标和风险解释，建议在原文获取稳定后接入远端 LLM，服务器不必本地部署模型。

LLM 只读取带 `document_id`、时间和来源的资料，输出固定 schema：事件角色、事实、来源片段、风险、未知项及解释。数字必须能回链原文，变化率由程序重算。网页内容属于不可信输入，不能指挥模型改变规则、调用工具或发送消息。

对主题关联、估值重估、挤空等解释标注为推断；没有独立证据不写成事实。“Strong”由版本化规则和数据质量闸门决定，不能仅接受模型一句“很强”。LLM 超时、JSON 无效或来源冲突时，退回规则报告和待核验状态，不阻塞行情循环。

后续需要的配置是提供方、API 地址、模型、日预算及服务器环境变量中的密钥。**现在不需要把密钥发到聊天里。** 只对新增或实质更新的候选调用模型，按内容哈希缓存，限制并发与费用。先以录制样例/固定响应测试，不为全市场每分钟调用一次 LLM。

## 5. 行情数据的放行条件

### 5.1 盘前价格和量

盘前价格必须是新鲜、时段正确的成交或明确标注的报价；以同一价格体系的前一常规 session 收盘计算 gap。区分最近成交、bid/ask、中间价和日线开盘价，不能混用。

v1A 中未知盘前量就显示未知，不能显示 0，也不能自动判薄。v1B 的同钟量拟采用美东 04:00 至当前完整分钟、历史 20 个有效 session 的相同窗口中位数；这只是拟定口径，尚未证明等同对方算法。

必须先获得并确认分子/分母的时段、交易所覆盖、竞价、零成交、重置、修订与缺失语义。盘口 bidSize/askSize 不是成交量；last tradeSize 的轮询相加不是完整成交量。历史不足和采集中断不能静默放行。

需要向数据商核实五件事：扩展分钟历史权限与获取方法；扩展 quote.volume 的累计边界；分钟与日线量差异原因；无 bar 是无成交还是缺数；行情/新闻/预期的延迟、修订和历史版本能力。确认现有产品不足后，再评估是否需要第二个行情源，不预先要求购买。

### 5.2 分钟确认

分钟指标必须先过 session、时区、已收盘、新鲜度、重复、缺口和成交量口径检查。09:30/09:31 缺失不能换成其他分钟冒充 OR1/OR5。形成中 bar 不参与正式触发。

后续触发优先把 OR5 做成单独可回放的规则：09:30-09:34 的已完成区间形成后，再看后续已完成 bar 是否穿越区间高点，同时满足 VWAP 与验证后的量能要求。不是“09:35 到时就发”。若采用下一根 1min 收盘确认，最早判定要等该 bar 完成并实际收到数据。

OR1/OR15 是显式配置的独立变体，不能因 OR5 缺数而无记录地切换。止损与市场风险闸门要保留，但本版不自动下单。持续高于杯沿、开盘后才穿杯沿、隔夜跳过杯沿应区分，不能统称 gap-through。

## 6. 状态、评级与通知隔离

观察生命周期建议为：`DISCOVERED -> EVIDENCE_PENDING -> WATCHING -> ALERT_CANDIDATE`，并允许 `EXPIRED` / `EXCLUDED`。流动性用独立字段表示 `UNKNOWN`、`THIN` 或经验证的 `SUFFICIENT`；价格触发另记 `NOT_EVALUATED`、`WAITING`、`DATA_INCOMPLETE`、`CONFIRMED`。

这不增加新的信号家族：现有 `CUP_HANDLE_BREAKOUT` 不变；事件观察归 `EP_WATCH`；只有对应杯形和跳空触发全部合格才是 `EP_GAP_THROUGH_CUP`。普通 EP 没有杯也可以继续观察，不冒充杯柄。

Strong/Moderate 是候选质量标签，不是盈利概率或入场命令。数据未知不能通过降低评级掩盖；应同时显示缺失字段。v1A 默认不发生产提醒。

后续 EP 使用独立 outbox 和专用频道，通知键至少包含事件 ID、session、信号家族和语义阶段。原文小幅重排不触发重发；实质证据变化或薄量到合格的升级有单独的变更规则与冷却。

现有 [`src/breakouts/live/state.py`](../src/breakouts/live/state.py) 的发送冷却按 ticker 查询已发消息。如果直接复用现有表和冷却，会压掉同股票的新阶段或其他家族提醒。可复用发送传输与重试模式，不能不加区分地复用去重语义。超时后发送结果不明要保留不确定状态，避免盲目重试重复通知。

## 7. SG 运行与资源边界

未来仅在确认后部署到 **SG `/home/projects/quant`、root、`.venv`**，采用独立 systemd service/timer；不创建本地 Mac 定时任务或 Codex 自动化。

建议初始调度：交易日前夜事件增量留存；盘前新闻每 5 分钟增量同步，行情仅对有预算的候选约每 60 秒更新；开盘后继续约每 60 秒评估观察池，以支持 VEEV 式升级。08:15 / 09:20 可以生成快照，但不应是唯二的发现时刻。这些是待测配置，不是已经部署的频率。

新闻/LLM 与分钟监控分开任务队列，限制并发，按事件内容缓存；任务禁止重叠，超过预算时记录未覆盖候选并在下轮补齐，不能悄悄只看前 40 只。行情与 LLM 使用不同超时，整轮设置总期限，429 尊重限流，403/challenge 不绕过。

2 核 4GB 是否足够必须在 SG 活跃交易时段测 CPU、RSS、周期 P95、队列等待、数据延迟和请求费用。当前本地探测中一个大区间请求耗时 52.38 秒，足以说明不能把新闻全文请求串行塞进每分钟价格循环。优先控制工作量，不假定升级硬件能解决数据问题。

## 8. 验收清单与执行顺序

| 步骤 | 交付/验收 | 当前状态 |
|---|---|---|
| 1. 验证数据能力 | 账户抽样、17 案例证据、缺口和实现边界 | 本轮完成；未覆盖 SG 实时与盘前累计量 |
| 2. 数据契约与固定案例 | 输入字段/时区/口径/schema、17 案例及 heads-up 测试、未知状态 | 待确认后实施 |
| 3. 独立 v1A 采集和分析 | 分片分页、原文容错、事件归属、事实验证、版本留存、shadow 报告 | 待开发 |
| 4. 行情补缺验证 | 活跃盘前采样、历史同钟量、分钟量口径、开盘缺口处理 | 正式量能评分和触发的前置条件 |
| 5. SG shadow | 独立服务、资源测量、全市场输入与排除原因、无真实推送 | 部署前需单独确认 |
| 6. 提醒和 gap-through | 独立通知状态/频道、升级去重、无未来信息的触发回放 | 单独放行，不跟随 v1A 自动开启 |

自动化测试至少覆盖：

- 给定事实的事件分类和字段可追溯；价格触发不读取后来才收到的公告、修订预期或日终数据。
- 4,000 条财报截断、100 条新闻分页、分钟长区间截断、重复 URL、律所公告、权证身份和财政年映射。
- GTLB/AGX 开盘缺口、NYAX 稀疏分钟、盘前量未知、零分母、负 EPS、GAAP/调整后口径冲突。
- VEEV 式候选保留和升级只发一次；不同家族不互相覆盖；shadow 不调用发送接口。
- 同 ticker、同来源时间但正文修订，能够记录版本并区分更正与新事件。
- 原文访问失败、LLM 失败、预算溢出都有原因记录，不影响既有杯柄和多因子测试。

17 个案例用于固定输入的能力验收，不可硬编码为全市场扫描名单。全市场召回必须使用时间窗口内真正取得的数据重放，另留未用于调参的日期，并保存候选全集和抓取范围，才能区分漏发现、证据缺失、规则排除和容量排除。

至少五个完整交易日的 shadow 可检查运行稳定性，但不能证明 EP 策略有效。催化和交易质量要在更长观察期、多种事件和市场环境中评估，建议覆盖完整财报季；累积约 50 个案例也只是研究起点，不是统计胜率保证。

## 9. 当前需要你决定什么

本轮无需提供 AI 密钥或额外购买数据。建议接下来确认 v1A 的隔离开发范围，同时核实数据商的盘前/分钟量口径。拿到可靠原文后再选择 AI 提供方和预算；拿到可靠扩展时段行情后再放行量能评级与开盘触发。

每一步都应能回答某只股票为什么没有出现：没被发现、超出抓取范围、行情缺失、证据未核准、策略不符、容量溢出，还是消息未成功发送。这个排查链应和候选报告同时实现，而不是上线后再补。
